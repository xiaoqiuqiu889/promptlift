# Prompt Lift 微信-like 第 6–10 轮自主优化报告

## 目标与边界

本轮在既有“处理 / 场景 / 服务 / 我的”四区信息架构上继续迭代，重点学习微信类成熟产品的操作确定性、状态透明度、设置归类和克制的视觉层级。

Prompt Lift 的产品本质仍是“Windows 任意输入框里的安全表达助手”，核心目的仍是“一起让表达变好”。本轮没有增加聊天、朋友圈、支付或小程序：

- 聊天与朋友圈会引入账号、关系链、内容历史和同步能力，不属于当前安全表达助手的必要能力。
- 支付会引入交易、风控与合规责任，与当前文本处理链路无关。
- 小程序式能力中心会扩大产品范围，并削弱“一次读取、一次优化、一次安全回填”的单一心智。
- 本轮补充的功能只服务当前定位：一键处理、快速切换、进度反馈、隐私说明和服务可用性确认。

## 基线诊断

既有五轮已完成四区导航、分组列表、父子页面、浅色扁平视觉和基础无障碍支持，但实机审计仍发现五个可提升点：

1. 用户进入“处理”页后只能改设置，不能直接发起本次优化。
2. 当前档位、场景和应用方式只是展示文本，查看后仍需到下方列表重复寻找入口。
3. 任务状态只出现在任务界面，功能中心顶部一直显示静态说明。
4. 安全说明归在“服务”，与用户理解中的隐私和个人偏好不一致。
5. 模型入口只显示“配置”，无法快速判断当前是否已保存凭据。

## Loop 6：把“处理”页变成真正的处理入口

### 具体改动

- 在“处理”页首位增加绿色主按钮“优化当前输入”。
- 按钮副标题实时显示当前场景与档位，例如“AI 提示词 · 清晰直达”。
- 主按钮下明确显示“只处理当前输入 · 不保存表达历史”。
- 点击后复用既有 `handleEnhance()`、模型调用和 CAS 安全回填链路，不增加第二套任务逻辑。
- 处理中按钮进入禁用与 `aria-busy` 状态，避免重复提交。

### 理由

成熟产品的首页必须既能确认状态，也能完成核心动作。原页面只有设置能力，用户进入后还要退出功能中心再点击小精灵，路径不闭环。

### 效果评估

- 从“处理页发起优化”的额外退出步骤由 1 步降为 0 步。
- 双击 Alt 和单击小精灵的零选择高频入口保持不变。
- 主操作使用单一绿色强调，其余设置继续使用中性色。
- 回归契约：`test/wechatLikeUiV2.contract.test.mjs` Round 6。

## Loop 7：让状态总览同时承担快捷导航

### 具体改动

- 将“档位 / 场景 / 应用”三个状态块升级为可点击快捷入口。
- 保留既有产品决策：优化档位第一、工作模式第二、应用方式第三。
- 点击档位或场景直接打开对应子页；应用方式使用可访问的 `switch` 语义。
- 每个快捷块获得至少 44px 的触达高度、明确的悬停态和键盘焦点态。

### 理由

只读摘要会迫使用户在同一页重复寻找同名设置。将摘要变为入口，符合“看见当前状态即可修改”的直接操作原则。

### 效果评估

- 从状态确认到对应设置的路径由“摘要 → 下方列表 → 设置页”缩短为“摘要 → 设置页”。
- 档位、场景和应用方式仍只有一个真实状态源，没有产生重复配置。
- 快捷区在 360×520 小窗中保持三等分、无截断和无横向溢出。
- 回归契约：`test/wechatLikeUiV2.contract.test.mjs` Round 7。

## Loop 8：把任务进度同步到功能中心

### 具体改动

- 功能中心顶部增加状态点和实时文字：
  - 就绪
  - 处理中
  - 待审阅
  - 已完成
  - 需处理
- 主按钮在处理中显示“正在优化…”和“原文保持不变，请稍候”。
- 状态由既有 `setStatus()` 单向同步，不额外推断任务结果。
- 审阅模式下生成成功但尚未应用时，显示“待审阅”，避免误报“已完成”。

### 理由

成熟产品不会让不同页面对同一任务呈现不同状态。用户从结果页进入功能中心后，仍应知道任务正在处理、等待审阅还是需要处理错误。

### 效果评估

- 状态反馈从任务局部扩展到全局导航，但仍使用同一个状态机。
- 加载期间主按钮不可重复触发，减少重复模型请求风险。
- 状态点采用灰、橙、绿、红的克制语义色，没有新增动画或装饰效果。
- 回归契约：`test/wechatLikeUiV2.contract.test.mjs` Round 8。

## Loop 9：重组“服务”与“我的”的信息归属

### 具体改动

- “服务”页只保留模型与 Key、连接检查和开机自启动。
- 将“安全与使用说明”移动到“我的 → 帮助与安全”。
- 一级文案调整为“隐私与安全”，摘要显示“本地保护”。
- 子页继续如实说明三项已实现能力：
  - 不保存输入内容或优化历史；
  - 应用前校验目标窗口与原文；
  - API Key 使用 Windows 加密存储。

### 理由

模型服务回答“系统是否可用”，隐私与安全回答“我的数据如何被处理”。两者分开后，用户更容易形成稳定的信息位置记忆。

### 效果评估

- “服务”页从两个分组收敛为单一模型与系统分组。
- “我的”页形成“身份 → 偏好 → 帮助与安全 → 应用”的自然层级。
- 没有新增未实现的云同步、账号安全或历史管理承诺。
- 回归契约：`test/wechatLikeUiV2.contract.test.mjs` Round 9。

## Loop 10：让模型服务状态可被一眼确认

### 具体改动

- 模型与 Key 行不再显示笼统的“配置”，改为实时状态：
  - 已配置：API Key 已通过 Windows 加密保存；
  - 待配置：当前没有可复用的加密凭据；
  - 仅本次：系统无法使用加密存储，Key 只在当前运行内存中可用。
- 状态文字使用 `aria-live="polite"`，配置保存或系统能力变化后同步刷新。
- 仍保留独立的“检查模型配置”动作，避免把“已保存”误写成“连接一定可用”。

### 理由

“已保存凭据”和“实时连接验证”是两个不同事实。成熟的设置页应显示真实状态，同时避免用过度乐观的“正常”掩盖尚未检查的网络或服务问题。

### 效果评估

- 用户无需进入配置页即可判断是否存在可复用凭据。
- 没有把“已配置”升级为“连接成功”，事实边界保持准确。
- 模型检查、配置保存和安全存储的原技术路径不变。
- 回归契约：`test/wechatLikeUiV2.contract.test.mjs` Round 10。

## 最终界面与体验结构

| 一级入口 | 用户问题 | 核心功能 |
| --- | --- | --- |
| 处理 | 现在按什么方式优化，能否立即开始？ | 一键处理、档位、场景、应用方式、任务状态 |
| 场景 | 这次是在对谁表达？ | AI 提示词、向上沟通、用户沟通、PPT 文案 |
| 服务 | 模型和系统是否准备好？ | 模型与 Key、连接检查、开机自启动 |
| 我的 | 我的偏好与数据如何处理？ | 小精灵、隐私与安全、退出 |
